# REVIEW.md — Defects found in the starter `app/main.py`

| # | Where (function / line) | What is wrong | How you'd notice it | How I fixed it |
|---|---|---|---|---|
| 1 | `list_employees` / line 93 | **Off-by-one in pagination**: `skip = page * page_size` skips `page_size` records even on page 1, so page 1 returns records from position 20 onward, not 0. | `GET /employees?page=1` returns an empty result when fewer than 20 employees exist. | Changed to `skip = (page - 1) * page_size`. |
| 2 | `list_attendance` / lines 144-150 | **Full-collection scan loaded into Python memory**: `db.attendance_logs.find(q)` fetches every matching document, sorts them in Python, then slices. On 100k records this is slow and memory-heavy, and `total = len(docs)` re-counts after the full load. | `GET /attendance` is slow and memory-hungry at scale. | Replaced with `count_documents` for `total` and `.sort().skip().limit()` for the page — server-side. |
| 3 | `list_attendance` / line 94 | `total = db.employees.count_documents({})` counts **all employees**, not the filtered attendance set; the bug means the wrong `total` is returned when filters are active. | `GET /attendance?emp_code=EMP0001` returns `total` equal to the entire employee count instead of that employee's record count. | Changed `total` to `db.attendance_logs.count_documents(q)` where `q` matches the applied filters. |
| 4 | `punch_in` / line 102 | **No time-zone awareness**: `datetime.fromtimestamp(ms/1000)` uses local system time (IST on this machine but UTC on a server), so the attendance date computed in line 103 is wrong in UTC-offset environments. | On a server running UTC, a punch at 23:45 IST (18:15 UTC) is dated the previous calendar day. | Replaced with `_ms_to_dt()` which uses `datetime.fromtimestamp(..., tz=timezone.utc)`, then derives the IST attendance date via `_attendance_date()`. |
| 5 | `punch_in` / line 104 | **Duplicate punch-in check is not atomic**: `find_one` then `insert_one` is a TOCTOU race — two concurrent requests can both pass the `find_one` check and both insert, violating the one-record-per-day guarantee. | Send two punch-in requests for the same employee at the same moment; both may succeed. | Removed the explicit `find_one` check; rely entirely on the unique compound index on `(emp_code, date)`. `insert_one` raises `DuplicateKeyError` → 409 atomically. |
| 6 | `punch_in` / line 113 | **`compute_late_minutes` can return negative**: if the punch-in is *before* shift start, `minutes` is negative, and `minutes if minutes > 10 else 0` returns 0 — OK in that case, but the logic is confusing and would silently return a negative value if the grace-period threshold were changed. Additionally the grace period was implemented as `> 10` minutes, but R2 says *strictly more than* 10 minutes (09:40:01 → 10, not 09:40:00). | `GET /attendance` would show `late_minutes = 10` for exactly 09:40:00 punch-in (9 minutes 60 seconds = 600 seconds = 10 minutes elapsed, which is NOT strictly more than 10 minutes). | Rewrote `_compute_late_minutes`: use `elapsed_seconds`, only late if `elapsed_seconds > 600`, then return `int(elapsed_seconds // 60)`. |
| 7 | `health` / line 73-74 | **Health check does not test MongoDB**: returns `{"status": "ok"}` unconditionally even if MongoDB is down. The openapi.yaml spec says "Returns 200 only if MongoDB answers a ping, otherwise 503". | Stop MongoDB; `GET /health` still returns 200. | Added `db.command("ping")` inside a try/except; returns 503 on failure. |
| 8 | `create_employee` / line 82 | **`created_at` stored as naive datetime**: `datetime.now()` returns a timezone-naive local datetime. PyMongo stores it as naive UTC if the machine is IST, which shifts the stored time 5h30m. | `created_at` returned in the API would be off by 5.5 hours. | Changed to `datetime.now(tz=timezone.utc)`. |
| 9 | `create_employee` — missing | **No unique index on `emp_code`**: the check relies on `find_one` (TOCTOU race). Concurrent duplicate creates could both insert. | Two simultaneous `POST /employees` with the same `emp_code` can both get 201. | Added `db.employees.create_index("emp_code", unique=True)` at startup; catch `DuplicateKeyError` → 409. |
| 10 | `list_employees` — missing | **No sort** on the result: items are returned in MongoDB insertion order, not `emp_code` ascending as required by the spec. | `GET /employees` returns employees in arbitrary order. | Added `.sort("emp_code", ASCENDING)` to the query chain. |
| 11 | `punch_in` — missing | **No 404 for unknown employee**: the original code calls `emp["shift_start"]` without guarding `emp is None`, causing an unhandled `TypeError`. | `POST /attendance/punch-in` with a non-existent `emp_code` crashes with 500. | Added `if not emp: raise HTTPException(404, ...)`. |
| 12 | All endpoints | **`punched_at` accepts second-level integers**: no validation that the epoch is in milliseconds (min 100,000,000,000). A seconds-level timestamp like `1720000000` would silently produce a date in 1974. | Send `"punched_at": 1720000000`; the API accepts it without error. | Added `EPOCH_MIN` / `EPOCH_MAX` validation in Pydantic `field_validator`. |
| 13 | `compute_overtime` / line 46 | **Overtime uses `datetime.fromisoformat(date_str)` without timezone**: mixes a naive datetime with a potentially aware `punch_out`, causing a `TypeError` at runtime on Python 3.11+. | Any punch-out request raises 500. | Rewrote `_compute_overtime_minutes` to build `end_ist` with explicit `tzinfo=IST` and handle overnight shifts correctly. |

## Things inspected and confirmed NOT defects

- `compute_work_hours` is arithmetically correct for normal shifts; the only issue was rounding (Python's `round()` uses banker's rounding which can differ from half-up). Fixed in `_half_up()`.
- The starter correctly initialises `punch_out`, `work_hours`, `history`, `half_day`, and `overtime_minutes` to their null/zero defaults on punch-in.
- `load_dotenv()` at the module top is correct; real environment variables always win.
